OAuth 2.0 vs OpenID Connect

OAuth 2.0 and OpenID Connect are modern protocols used by an Application and Azure Active Directory to communicate with each other — to grant access to resources and verify user identity respectively.

OAuth 2.0 — Authorization

  • Used to grant an application access to a resource (e.g. Microsoft Graph API)
  • Returns an Access Token — used to call APIs
  • Does not tell you who the user is
  • scope: https://graph.microsoft.com/User.Read
  • response_type: code
  • Two flows: Authorization Code (user) and Client Credentials (service)

OpenID Connect — Authentication

  • Built on top of OAuth 2.0 — adds user identity
  • Returns an ID Token containing user claims (name, email, etc.) plus an Access Token
  • Used to verify who the user is — Sign In / SSO
  • scope: openid (required — V2.0 endpoint requires scopes)
  • response_type: code id_token
  • The ID Token is the proof that OpenID Connect is an Authentication Protocol
Key rule: Both OAuth 2.0 and OpenID Connect use the same two Azure AD endpoints — the Authorize Endpoint and the Token Endpoint. The difference is in the scope and response_type parameters you send.

OAuth 2.0 — Authorization Code Flow

The Authorization Code Flow is used when a user needs to log in and grant an application permission to access resources on their behalf (e.g. reading their profile from Microsoft Graph). It involves two phases: the user authenticates at the Authorize Endpoint, then the application exchanges the returned code for an Access Token at the Token Endpoint.

When to use: When a user is present and the application needs to access Microsoft Graph or another API on their behalf.

  &redirect_uri=http://localhost/
  &scope=https://graph.microsoft.com/User.Read
3
Azure AD: Prompts user to sign in and accept consent
Azure AD presents its login page at the Authorize Endpoint. The user is prompted to enter their credentials (username & password). After authentication, Azure AD shows a consent screen listing the permissions the application is requesting — in this case, User.Read (read the user's profile). The user must accept the consent to proceed.
↓ User signs in and consents → Azure AD generates a one-time authorization code
4
Azure AD Authorize Endpoint → Application: Returns authorization code
Azure AD redirects the browser back to the application's redirect_uri with a short-lived authorization code in the URL. This code is a one-time-use value — it is not the Access Token. It must be exchanged at the Token Endpoint to get actual tokens. 
http://localhost/
  ?code=OAAABAAAIL9Kn2227UulwVFPbm0gLWQJVzCTE9UkP3p5x1aXxUjq3n8b2JRLk4OVXr...
↓ Application receives the code — now exchanges it at Token Endpoint (back-channel)
5
Application → Azure AD Token Endpoint: Exchange code for Access Token
The application makes a direct server-to-server POST to the Token Endpoint — this call never goes through the browser. The application proves its identity using its Client Secret and sends the code received in step 4. All highlighted values are required: 
POST https://login.microsoftonline.com/conceptswork.com/oauth2/v2.0/token

  client_id     = 6731de76-14a6-49ae-97bc-6eba6914391e
  scope         = https://graph.microsoft.com/User.Read
  code          = OAAABAAAIL9Kn2227UulwVFPbm0gLWQJVzCTE9UkP3p5x1aXxUjq3n8b2JRLk4OVXr...
  redirect_uri  = https://localhost/
  grant_type    = authorization_code
  client_secret = JqQX2PNo9bpM0uEIhUPzyrh
6
Azure AD Token Endpoint → Application: Returns Access Token
Azure AD validates the code, client_id, and client_secret. On success it returns an Access Token. The application now uses this token to call the Microsoft Graph API (or any other resource) on behalf of the user. The token is included in the Authorization: Bearer <token> header of every API request.

OAuth 2.0 — Client Credentials Flow

The Client Credentials Flow is used by Service Applications and Daemons — background services, automation scripts, or APIs that run without a user. The application authenticates using its own Client ID and Client Secret directly at the Token Endpoint. No Authorize Endpoint, no login page, no user consent.

When to use: Daemon processes, scheduled jobs, service-to-service calls, automation pipelines — any scenario where there is no interactive user. Client ID and Client Secret are required parameters.

Service Application → Azure AD Token Endpoint: Request token directly
There is no user, no browser, and no Authorize Endpoint involved. The service application posts its own Client ID and Client Secret directly to the Token Endpoint to authenticate as itself and request an Access Token. 
POST https://login.microsoftonline.com/conceptswork.com/oauth2/v2.0/token

  client_id     = 535fb089-9ff3-47b6-9bfb-4f1264799865
  scope         = https://graph.microsoft.com/.default
  client_secret = qWgdYAmab0YSkuL1qKv5bPK
  grant_type    = client_credentials
2
Azure AD validates and returns Access Token
Azure AD validates the client_id and client_secret. If valid, it returns an Access Token representing the service application's own identity — not a user's identity. The token is sent directly back to the service application.
3
Service Application: Uses Access Token to call the API
The service application uses the Access Token to make authenticated API calls with Authorization: Bearer <access_token>. The scope .default means the application uses all the API permissions that were pre-configured in its Azure AD app registration.
ParameterValue (Conceptswork example)What it means
client_id 535fb089-9ff3-47b6-9bfb-4f1264799865 The service application's unique Azure AD App Registration ID
scope https://graph.microsoft.com/.default .default means — use all permissions pre-granted to this app in Azure AD. There is no per-user consent.
client_secret qWgdYAmab0YSkuL1qKv5bPK The application's password — authenticates the service to Azure AD
grant_type client_credentials Tells Azure AD this is the Client Credentials flow — no user involved
OpenID Connect — Authentication Flow

OpenID Connect is built on top of OAuth 2.0 and uses the same two endpoints (Authorize and Token). The difference is that OpenID Connect adds scope=openid and uses response_type=code id_token, which causes Azure AD to return an ID Token alongside the authorization code.

The ID Token is what makes OpenID Connect an Authentication Protocol. It is a signed JWT containing user claims — the user's identity (name, email, object ID, etc.). The application uses it to verify who the user is. Without OpenID Connect, OAuth 2.0 only tells you what the user approved — not who they are.
Important — V2.0 endpoint requires scopes: The Azure AD v2.0 endpoint (/oauth2/v2.0/authorize) requires the scope parameter to be explicitly set. For OpenID Connect, scope=openid is mandatory. Without it, no ID Token is returned.

1
User opens the Application
User navigates to https://application.com. No active session exists. The application initiates the OpenID Connect flow.
↓ Application builds the OIDC authorize request
2
Application → Azure AD Authorize Endpoint: Redirect to sign in
The application redirects the browser to the Authorize Endpoint. The key difference from OAuth 2.0 is: response_type=code id_token (returns both a code and an ID Token) and scope=openid. 
https://login.microsoftonline.com/conceptswork.com/oauth2/v2.0/authorize
  ?client_id     = 673121de76-14a6-49ae-97bc-6eba6914391e
  &response_type = code id_token          ← requests both code AND ID Token
  &redirect_uri  = http://localhost/
  &scope         = openid                 ← mandatory for OpenID Connect
3
Azure AD: Authenticates the user — consent screen
Azure AD presents the login page. The user enters credentials. Azure AD then shows a consent screen. The user approves the consent to allow the application to read their identity.
↓ User approves consent → Azure AD returns code + ID Token
4
Azure AD Authorize Endpoint → Application: Returns ID Token + code
Because response_type=code id_token was requested, Azure AD returns two things to the application:

① ID Token — a signed JWT containing User Claims (name, email, object ID, tenant, etc.). This is what proves who the user is. The application reads the ID Token immediately to establish the user's identity.

② Authorization Code — same as OAuth 2.0. Used in the next step to get an Access Token.
5
Application: Reads the ID Token — user is authenticated
The application validates and reads the ID Token. The ID Token is a JWT — it contains signed user claims such as name, email, and unique user ID. This is the OpenID Connect authentication step: the application now knows who is logged in. No further call is needed to verify identity.
↓ Application sends authorization code to Token Endpoint to get Access Token
6
Application → Azure AD Token Endpoint: Exchange code for Access Token
The application POSTs the authorization code to the Token Endpoint (same as OAuth 2.0 step 5) to obtain an Access Token for calling APIs.
7
Azure AD Token Endpoint → Application: Returns Access Token
Azure AD returns an Access Token. The application now has both the user's identity (from the ID Token) and the permission to call APIs (from the Access Token).
OpenID Connect — Parameter Reference
ParameterValueWhat it means
client_id 673121de76-14a6-49ae-97bc-6eba6914391e The registered application's ID in Azure AD
response_type code id_token Requests both an authorization code and an ID Token from the Authorize Endpoint. This is what distinguishes OIDC from plain OAuth 2.0 (response_type=code).
redirect_uri http://localhost/ Where Azure AD sends the response. Must be pre-registered in the app.
scope openid Mandatory for OpenID Connect. Tells Azure AD to include an ID Token in the response. The V2.0 endpoint requires scopes to be explicitly specified.
id_token JWT (signed) Returned from the Authorize Endpoint alongside the code. Contains user claims (name, email, object ID, tenant ID, etc.). Used to verify the identity of the user. This is the core of OpenID Connect as an Authentication Protocol.
