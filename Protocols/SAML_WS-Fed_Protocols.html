SAML & WS-Federation Protocols

A complete reference for how SAML 2.0 and WS-Federation authentication protocols work — covering federation concepts, end-to-end request flows, URL parameters, authentication methods, and token responses, with real ADFS / Azure AD examples.

SAML 2.0 WS-Federation
What is Federation?
"Access to protected resources can be granted to 'security principals' existing in different realms."

Federation is the mechanism that allows a user authenticated in one domain (realm) to access resources in a completely different domain — without needing a separate account or re-entering credentials. The two domains establish a trust relationship, and identity is communicated via a token containing claims.

Core Components
Component In WS-Fed In SAML Role
Identity Store ADFS / Azure AD Identity Provider (IdP) Validates the user's credentials and issues a security token containing claims
Application Relying Party (RP) Service Provider (SP) The protected resource that trusts the identity store and grants access based on the token
Security Principal User / Browser / Service The entity requesting access — identified by claims
Claims Name, Email, Contact Number, Address, Groups… Attributes about the security principal, carried inside the token
Key principle: The Application never sees the user's password. It only receives a signed token from the trusted Identity Provider. The trust is configured once at the infrastructure level (Relying Party Trust in ADFS / Enterprise Application in Azure AD).
How the Protocols Work

WS-Fed and SAML are both federation protocols that enable an Application and an Identity Provider to communicate. They differ in message format, URL structure, and token version — but share the same fundamental flow.

Core Mechanism (Both Protocols)
Browser / User
Application (SP / RP)
ADFS / Azure AD (IdP / STS)
1
User navigates to the application
User opens browser and goes to https://application.com. The application checks: "Is this user already authenticated?"
↓ No active session found
2
Application redirects to the Identity Provider
The application detects no authenticated session and sends an HTTP 302 redirect to a specific endpoint of ADFS / Azure AD. The redirect URL includes protocol-specific parameters (see WS-Fed and SAML sections below) that tell the IdP: who is asking, what app, and what authentication method to use.
↓ Browser follows redirect to IdP
3
ADFS / Azure AD authenticates the user
The IdP presents a login page (or performs Windows Integrated Auth / MFA / Certificate auth silently). The user submits credentials. ADFS / Azure AD validates them against Active Directory or its user store.
↓ Authentication successful → SOAP request/response encoded in HTTPS
4
ADFS / Azure AD issues a security token (RSTR)
The IdP generates a signed security token — a Request Security Token Response (RSTR) — containing the user's claims (Name, Email, Groups, etc.). The token is embedded in an HTML auto-submit form and POSTed back to the application's endpoint via the browser.

WS-Fed returns a SAML 1.0 token.   SAML returns a SAML 2.0 assertion.
↓ Browser auto-POSTs token to application
5
Application validates the token and grants access
The application receives and validates the signed token (checks signature, issuer, audience, expiry). If valid, it establishes a local session and grants the user access. The user is now logged in without ever sending their password to the application.
WS-Federation

WS-Federation is part of the WS-* (Web Services) family of standards, developed by Microsoft and IBM. It is the native federation protocol used by ADFS (Active Directory Federation Services) and supported by Azure AD. It primarily targets browser-based SSO scenarios (Passive Requestor Profile) and rich-client / service scenarios (Active Requestor Profile via WS-Trust SOAP).

WS-Federation Key Facts

  • Protocol family: WS-* (WS-Federation 1.1 / 1.2)
  • Common Identity Provider: ADFS, Azure AD / Entra ID
  • Token issued: SAML 1.0 (wrapped in RSTR)
  • Transport: HTTPS with SOAP for Active Profile; HTTP redirect/POST for Passive Profile
  • Common applications: SharePoint, Exchange, Office 365 (legacy), custom .NET apps
WS-Federation — Request Flow
Passive Requestor Profile (Browser-Based SSO)
Browser / User
Relying Party (RP)
STS — ADFS / Azure AD
1
User → Relying Party: Access request
User navigates to https://application.com. The RP finds no session cookie.
2
Relying Party → Browser: HTTP 302 redirect to STS
The RP redirects the browser to the ADFS / Azure AD WS-Fed endpoint with these parameters: 
https://sts.conceptswork.com/adfs/ls/
  ?wa=wsignin1.0
  &wtrealm=urn:microsoft:adfs:claimsxray
  &wauth=urn:oasis:names:tc:SAML-1.0:am:password
  &wreply=https://application.com/auth/callback
  &wctx=originalUrl%3D%2Fdashboard
3
STS: Authenticates the user
ADFS / Azure AD receives the request. It reads wtrealm to look up the Relying Party Trust configuration. It then challenges the user for credentials using the method specified in wauth (password form, Windows auth, certificate, MFA).
4
STS: Issues SAML 1.0 token (RSTR)
After successful authentication, the STS builds a RequestSecurityTokenResponse (RSTR) containing a signed SAML 1.0 token with the user's claims. It wraps this in an HTML page with a hidden form field named wresult.
5
Browser → Relying Party: Auto-POST token
The browser auto-submits the form (via JavaScript) to the RP's wreply endpoint. The POST body contains:
wa=wsignin1.0&wresult=<RSTR with SAML 1.0 token>&wctx=...
6
Relying Party: Validates token & grants access
The RP validates the SAML 1.0 token signature, issuer, audience restriction, and token expiry. On success, it creates a local session and redirects the user to the originally requested resource.
WS-Federation — URL Parameters
Parameter Full Name Purpose Example Value
wa Web Action Specifies the action — always wsignin1.0 for sign-in wsignin1.0
wtrealm Web Realm (Relying Party Identifier) Identifies which Relying Party is making the request. Must match exactly what is configured in the Relying Party Trust on ADFS / Azure AD. This value never changes — it is saved in the RP trust configuration. urn:microsoft:adfs:claimsxray
wreply Web Reply URL The callback URL on the RP where the STS will POST the token response https://app.com/auth/wsfed
wauth Web Auth (Authentication Method) Requests a specific authentication method from the STS. See the Authentication Methods table for all values. urn:oasis:names:tc:SAML-1.0:am:password
wctx Web Context Opaque context value passed through by the STS unchanged — used by the RP to restore state after login (e.g., original URL) originalUrl%3D%2Fdashboard
wresult Web Result The RSTR (token response) POSTed back to the RP by the browser. Contains the SAML 1.0 token. <RequestSecurityTokenResponse>…</>
whr Web Home Realm Hints to the STS which home realm/IdP the user belongs to — skips the realm discovery page urn:federation:MicrosoftOnline
Identity Provider Endpoint (ADFS):
WS-Fed sign-in endpoint: https://sts.conceptswork.com/adfs/ls/
Azure AD WS-Fed endpoint: https://login.microsoftonline.com/<tenant-id>/wsfed
SAML 2.0

SAML (Security Assertion Markup Language) is an open standard developed by OASIS. Version 2.0 is the dominant standard for enterprise web SSO today. It uses XML-based assertions to communicate identity information between an Identity Provider (IdP) and a Service Provider (SP).

SAML 2.0 Key Facts

  • Standard body: OASIS (Security Assertion Markup Language 2.0)
  • Common Identity Provider: ADFS, Azure AD / Entra ID, Okta, Ping
  • Token issued: SAML 2.0 Assertion (XML)
  • Transport: HTTP Redirect (AuthnRequest) + HTTP POST (SAMLResponse)
  • Common applications: Salesforce, ServiceNow, AWS, any SAML SP-capable app
SAML 2.0 — Request Flow
IdP-Initiated SSO Flow (ADFS)

In the ADFS / Azure AD context, the SAML flow is commonly IdP-Initiated — the IdP begins the flow by sending the user directly to the SP with a pre-built assertion. This is triggered via the IdpInitiatedSignOn endpoint.

Browser / User
Service Provider (SP)
IdP — ADFS / Azure AD
1
User → SP: Access request
User navigates to https://application.com. The SP detects no active session.
2
SP → Browser: HTTP 302 redirect to IdP (IdpInitiatedSignOn)
The SP redirects the browser to the ADFS SAML endpoint: 
https://sts.conceptswork.com/adfs/ls/IdpInitiatedSignOn
  ?LoginToRP=urn:microsoft:adfs:claimsxray
  &RequestedAuthenticationContext=urn:oasis:names:tc:SAML-2.0:ac:classes:Password
3
IdP: Looks up Relying Party Trust & authenticates user
ADFS reads LoginToRP to find the matching Relying Party Trust (same identifier configured during trust setup). It then authenticates the user using the method specified in RequestedAuthenticationContext.
4
IdP: Generates & signs SAML 2.0 Assertion
After authentication succeeds, ADFS builds a signed XML SAMLResponse containing a SAML 2.0 Assertion with the user's claims. The response is base64-encoded and embedded in an HTML form.
5
Browser → SP: Auto-POST SAMLResponse
The browser auto-submits the form to the SP's Assertion Consumer Service (ACS) URL. POST body: SAMLResponse=<base64-encoded XML assertion>
6
SP: Validates assertion & grants access
The SP decodes the SAMLResponse, verifies the XML signature against the IdP's certificate, checks the audience restriction, validates NotBefore/NotOnOrAfter conditions, then creates a session and grants access.
SP-Initiated SSO Flow

In SP-Initiated flow, the SP generates an AuthnRequest and sends it to the IdP via an HTTP Redirect.

#ActorActionTechnical Detail
1 User Accesses SP Navigates to https://application.com — no session exists
2 SP Generates AuthnRequest SP creates a signed XML <AuthnRequest>, base64 + URL-encodes it, and sends HTTP 302 redirect to the IdP's SSO URL with SAMLRequest=…
3 IdP Parses AuthnRequest Decodes and verifies the AuthnRequest, checks the Issuer matches a registered SP
4 IdP Authenticates user Presents login page or performs silent Windows/MFA auth per the RequestedAuthnContext
5 IdP Issues SAMLResponse Builds signed XML SAMLResponse with SAML 2.0 Assertion, base64-encodes it
6 Browser Auto-POSTs to ACS Browser posts SAMLResponse to the SP's Assertion Consumer Service endpoint
7 SP Validates & grants access Verifies signature, audience, time conditions → creates session → redirects to resource

Sample Requests — WS-Fed vs SAML

WS-Federation Request

https://sts.conceptswork.com/adfs/ls/
?wa=wsignin1.0
&wtrealm=urn:microsoft:adfs:claimsxray
&wauth=urn:oasis:names:tc:SAML-1.0:am:password
  • Endpoint: /adfs/ls/
  • RP Identifier param: wtrealm
  • Auth method param: wauth

SAML Request

https://sts.conceptswork.com/adfs/ls/IdpInitiatedSignOn
?LoginToRP=urn:microsoft:adfs:claimsxray
&RequestedAuthenticationContext=
  urn:oasis:names:tc:SAML-2.0:ac:classes:Password
  • Endpoint: /adfs/ls/IdpInitiatedSignOn
  • RP Identifier param: LoginToRP
  • Auth method param: RequestedAuthenticationContext
Relying Party Identifier — stays the same in both:
wtrealm=urn:microsoft:adfs:claimsxray  /  LoginToRP=urn:microsoft:adfs:claimsxray

This value is saved once in the Relying Party Trust configuration and never changes regardless of which protocol is used.
Authentication Methods — Request Header Values

Both protocols allow the application to specify how the user must authenticate by including an authentication method parameter in the redirect URL. WS-Fed uses wauth; SAML uses RequestedAuthenticationContext.

Username & password login form		 urn:oasis:names:tc:SAML:1.0:am:password urn:oasis:names:tc:SAML:2.0:ac:classes:Password

Response — RSTR (Request Security Token Response)

After the Identity Provider authenticates the user, it sends back a Request Security Token Response (RSTR) containing the security token. The key difference between WS-Fed and SAML is the token version inside the response.

WS-Federation Response

  • Response type: RSTR (RequestSecurityTokenResponse)
  • Token inside: SAML 1.0 Token
  • Delivered via: HTTP POST form field wresult
  • Token is XML, signed by ADFS certificate
  • Contains claims: Name, Email, Groups, etc.

SAML Response

  • Response type: SAMLResponse
  • Token inside: SAML 2.0 Assertion
  • Delivered via: HTTP POST form field SAMLResponse
  • Assertion is XML, signed (and optionally encrypted)
  • Contains: AuthnStatement, AttributeStatement, Conditions
SAML 2.0 Assertion Structure
<!-- SAMLResponse — base64-decoded XML -->
<samlp:Response xmlns:samlp="urn:oasis:names:tc:SAML:2.0:protocol"
                 ID="_abc123" Version="2.0"
                 IssueInstant="2024-01-15T10:00:00Z"
                 Destination="https://application.com/saml/acs">

  <saml:Issuer>https://sts.conceptswork.com/adfs/services/trust</saml:Issuer>

  <samlp:Status>
    <samlp:StatusCode Value="urn:oasis:names:tc:SAML:2.0:status:Success"/>
  </samlp:Status>

  <saml:Assertion ID="_assertion456" Version="2.0">

    <!-- Who issued this assertion -->
    <saml:Issuer>https://sts.conceptswork.com/adfs/services/trust</saml:Issuer>

    <!-- XML Signature — validates token was not tampered with -->
    <ds:Signature>...</ds:Signature>

    <!-- Time validity + audience restriction -->
    <saml:Conditions NotBefore="2024-01-15T09:58:00Z"
                     NotOnOrAfter="2024-01-15T10:58:00Z">
      <saml:AudienceRestriction>
        <saml:Audience>urn:microsoft:adfs:claimsxray</saml:Audience>
      </saml:AudienceRestriction>
    </saml:Conditions>

    <!-- How and when the user was authenticated -->
    <saml:AuthnStatement AuthnInstant="2024-01-15T10:00:00Z">
      <saml:AuthnContext>
        <saml:AuthnContextClassRef>
          urn:oasis:names:tc:SAML:2.0:ac:classes:Password
        </saml:AuthnContextClassRef>
      </saml:AuthnContext>
    </saml:AuthnStatement>

    <!-- User's claims / attributes -->
    <saml:AttributeStatement>
      <saml:Attribute Name="http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name">
        <saml:AttributeValue>sushanth.kummari@company.com</saml:AttributeValue>
      </saml:Attribute>
      <saml:Attribute Name="http://schemas.microsoft.com/ws/2008/06/identity/claims/groups">
        <saml:AttributeValue>IAM-Admins</saml:AttributeValue>
      </saml:Attribute>
    </saml:AttributeStatement>

  </saml:Assertion>
</samlp:Response>
SAML vs WS-Federation — Comparison
Aspect WS-Federation SAML 2.0
Standard Body WS-* (Microsoft / IBM) OASIS
Token Issued SAML 1.0 token (inside RSTR) SAML 2.0 Assertion
Response Container RSTR (RequestSecurityTokenResponse) SAMLResponse
IdP / STS Endpoint /adfs/ls/ /adfs/ls/IdpInitiatedSignOn
RP Identifier Parameter wtrealm LoginToRP
Auth Method Parameter wauth RequestedAuthenticationContext
Sign-in Action Parameter wa=wsignin1.0 Not required (endpoint implies it)
Context / State Parameter wctx RelayState
Primary Ecosystem Microsoft (SharePoint, Exchange, .NET) Cross-platform (Salesforce, AWS, Okta, etc.)
Best Used For Legacy Microsoft apps, ADFS-native integrations Modern cross-platform SSO, cloud apps
Bottom line: Both protocols achieve the same result — federated SSO via ADFS / Azure AD. The RP Trust configuration identifier (urn:microsoft:adfs:claimsxray) is identical in both; only the endpoint URL and parameter names differ. Choose WS-Fed for legacy Microsoft apps; choose SAML 2.0 for modern cloud applications and cross-platform integrations.
